## Subject

OpenFOAM v2512 `renumberMesh` multi-node finalisation failure with signal 7 on ASPIRE2A

## Technical summary

We are diagnosing a reproducibility problem in OpenFOAM.com v2512 on ASPIRE2A.

The workload is the `occDrivAerStaticMesh` case with approximately 65 million
cells. The diagnostic scope is limited to:

```text
decomposePar
→ renumberMesh -constant -overwrite -parallel
```

No `potentialFoam`, `applyBoundaryLayer`, or `simpleFoam` was run in these
diagnostic jobs.

The OpenFOAM environment was consistently:

```text
OpenFOAM: openfoam/2512
Compiler: GCC 11.2.0
MPI: Cray MPICH 8.1.15
Launcher: PALS mpirun 1.1.6
OMP_NUM_THREADS=1
```

The launch form was:

```bash
mpirun -n <NPROCS> --ppn <RANKS_PER_NODE> \
    --cpu-bind depth -d 1 \
    renumberMesh -constant -overwrite -parallel
```

All T1, T2, and T4 cases were freshly copied from the pristine source case and
freshly decomposed. The pristine source was not modified.

## Failure pattern

The failed rank and failed node vary between attempts. The failure consistently
appears after:

```text
End
Finalising parallel run
```

No run produced:

- `FOAM FATAL ERROR`;
- NaN diagnostics;
- explicit floating-point exception text;
- explicit MPI error;
- explicit PALS error.

T1 and T4 both use 128 total MPI ranks:

```text
T1: 1 node × 128 ranks → PASS
T4: 2 nodes × 64 ranks → FAIL
```

This makes multi-node execution or inter-node runtime behavior a stronger
suspect than total rank count alone. T2 also fails at 256 ranks on two nodes.
The evidence does not yet identify whether the responsible layer is PALS,
Cray MPICH, node/runtime handling, inter-node transport, or an application/runtime
interaction during finalisation.

## Information requested from NSCC

Could NSCC please check:

1. PBS MOM logs for the relevant jobs.
2. PALS server-side launcher/session logs.
3. The precise termination reason corresponding to signal 7.
4. Whether signal 7 was generated by:
   - application process termination;
   - node/runtime intervention;
   - memory protection;
   - PALS cleanup;
   - MPI transport failure; or
   - another system-level mechanism.
5. Whether there are node-level hardware or runtime events for the failed nodes.
6. Whether there are known Cray MPICH 8.1.15 / PALS 1.1.6 / OpenFOAM v2512
   compatibility issues.
7. Whether this finalisation failure pattern is known for large uncollated
   OpenFOAM cases.
8. Whether additional user-visible diagnostic variables or launcher flags should
   be enabled for a controlled reproduction.

We are not requesting a change to compiler, MPI, binding, or application
settings. The immediate goal is only to determine the cause of the signal-7
termination.

  every possible binding or topology effect.
- No alternate MPI implementation was tested.
- No compiler or OpenFOAM optimization was performed.
- The evidence does not confirm that PALS or Cray MPICH is defective.
- The signal-7 mechanism remains unresolved without server-side/platform data.
